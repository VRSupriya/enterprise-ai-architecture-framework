# Agentic Systems Architect — fsa-review-fixture — Round 1

## Verdict
**Not viable as proposed.** The six-agent design fails the agentic justification test (`standards/agentic-ai-design-principles.md` §1.1 and §1.2). Every requirement has a path you can list in advance. R1 is grounded Q&A. R2 and R3 are structured writes that already exist as production n8n flows (INV-001). R4 is a fixed notification. Nothing in R1–R4 calls for dynamic planning, and none of the six agents has its own context, permission set or owning team. The implemented config (`config/agents.yaml`) is riskier than the document. It configures a delete tool nobody asked for (Q-002), a shared ERP admin account, unlimited retries on non-idempotent create calls, no iteration limit, and business limits that live only in a prompt. **Recommended shape:** rung 2 deterministic orchestration (reuse n8n for every ERP write), with a rung 5 RAG step for R1 and rung 4 LLM steps for intent classification and drafting work-order fields. Each write needs technician confirmation of the exact parameters. Agent runtime: none. Rung 6 is rejected for now, and §Recommendations gives a narrow, evaluation-gated condition for a read-only agent later.

## Recommendations

### Decision 1 — Agentic shape (ladder)
**Recommended: rung 2 orchestration + rung 5 RAG + rung 4 LLM steps. No agent loop.** (R1–R4, AP-03, AP-11, INV-001, ASM-003)

| Rung | Verdict | Reason |
|---|---|---|
| 0 Process change / configure existing | Rejected as the whole solution; partly used | Call reduction (OBJ-01) needs technician self-service, which the current dispatch-desk process can't give. The existing n8n create/update flows are reused as the write path. |
| 1 Deterministic app / rules | Used for R3, R4, and all limits | Status update is an enumerated choice (work-order id + status transition). Escalation is a button or intent with a fixed template. Rules alone can't handle free-text manual questions (R1) or work-order details given conversationally (R2). |
| 2 Workflow automation | **Selected as the orchestrator** | Intents are a known set (ask / create / update / escalate) and each has a fixed sequence. n8n already owns the ERP writes. |
| 3 Search / conventional ML | Rejected as the whole solution for R1 | Technicians need synthesized answers with citations across manuals and history, not ranked links. |
| 4 LLM step in workflow | **Selected** for intent classification and for extracting R2 fields into a typed draft | It takes unstructured input and produces structured output, which deterministic code then validates. |
| 5 RAG | **Selected for R1** | Answers must be grounded in governed manuals and maintenance history, fetched by parameterized lookups. |
| 6 Single bounded agent | **Rejected now** | Paths can be listed. No requirement has tool selection that depends on intermediate results in ways a fixed "retrieve manuals + fetch asset history" step can't cover. There is no autonomy metric (§1.1). Re-open only for a **read-only** R1 Q&A agent, and only if offline evaluation (F-AG-11) shows that fixed retrieval measurably fails on multi-hop questions. Write tools are permanently out of its scope. |
| 7 Multi-agent | **Rejected** | Fails every §1.2 item: work is not separable by context, permission or owner, there is no parallelism benefit, and coordination and latency costs are not accounted for. |

**Rejected: LangGraph multi-agent on AKS (PREF-001).** Requirements don't justify it, and ASM-003 adds operational risk. **Alternative, only if the team wants it:** a single LangGraph `StateGraph` used purely as a deterministic workflow (fixed nodes, no LLM routing). That is acceptable but adds learning cost the requirements don't need. Plain Python service + n8n is the decisive recommendation.

### Decision 2 — Planning vs execution boundary
| Decision | Owner |
|---|---|
| Classify intent (ask / create / update / escalate / out-of-scope) | Model (rung 4), with an "unclear → ask the user" fallback |
| Which data to retrieve for R1 | Deterministic: always manuals search + asset history for the asset in context |
| Answer wording and citation | Model (rung 5), grounding checked deterministically |
| Work-order field values | Model extracts, deterministic schema validation |
| Priority allowed, count cap, asset exists, status transition valid | **Deterministic code** (AP-14) |
| Whether the write executes | **Technician confirmation** of exact payload + authorization outside the model |
| Retry / escalate | Deterministic policy |

| Tool / step | Side effect | Permission | Authorization point (outside model) | Approval required |
|---|---|---|---|---|

| `erp_delete_work_order` | — | — | — | **Removed** (Q-002) |
| `sql_query` | — | — | — | **Removed**, replaced by the typed reads |

### Decision 4 — Bounds
At most 3 LLM calls per turn. A per-request token budget is enforced at the model gateway. Each step has a timeout that fits NFR-A (to be set by reliability). Writes get at most 2 idempotent retries. Every breach leads to a defined terminal state and an escalation offer. A per-day cost alert goes to the owner.

### Decision 5 — Evaluation
An offline set with release thresholds, run on every version change (F-AG-11, F-AG-14). It covers intent accuracy, field-level extraction accuracy, groundedness and citation, refusal and out-of-scope behaviour, injection planted in manuals and history, limit exhaustion, and duplicate-submit tests.

## Positions for the Board
- **Solution / enterprise architect:** I expect agreement that n8n stays the system of execution for ERP writes (INV-001, AP-04). Whether n8n runs inside the mandated Azure estate and region (CON-001/002) is not stated, so please confirm.
- **Security & identity:** F-AG-04 and F-AG-10 set the permission scope I need (create-only / update-status-only, technician entitlement check). Security owns the mechanism: delegated identity, workload identity for the app, removing the shared admin account. Gateway keys in a config map (`agents.yaml` llm.api_key) are a credential finding for them.
- **Data / knowledge / memory:** `deployment_region: eastus` vs CON-002 is a constraint conflict for platform/data to rate, probably Critical and blocking G3. Pinecone (PREF-002) residency is theirs. Logging full prompts and responses (with customer data) for 730 days is a retention and minimisation issue for them. My only requirement is a structured trajectory log, not raw-prompt retention.
- **AI platform:** a custom in-house gateway (PREF-003) for one use case conflicts with AG-12 and §6. I recommend an existing Azure gateway capability, and the platform specialist should decide which. The removal of AKS-hosted agent runtime follows from my ladder verdict.
- **Reliability:** idempotency-key support in the n8n/ERP flows is the key dependency for F-AG-05. If the ERP can't honour keys, a dedupe check in n8n (lookup before create) is the fallback. Reliability owns that design.
- **Possible dissent (sponsor or PREF-001 advocates):** "multi-agent scales to future use cases." I would only revise the verdict with evaluation evidence of a requirement whose paths can't be listed, or a second use case with distinct permissions or owners.
