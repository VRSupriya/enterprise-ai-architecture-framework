# Red Team Architect — fsa-review-fixture — Round 1

## Verdict

**Not viable as proposed.** The design has four separate paths to an unauthorized or duplicated work-order change in the ERP, and each one can be reached through normal input:

1. The Work Order Agent holds a shared ERP **admin** account and a **delete** tool that no requirement asks for.
2. The only business limits (at most 3 work orders, never EMERGENCY) live in the system prompt, and no technician approval step exists.
3. It retries non-idempotent creates without limit.
4. Indirect prompt injection through manuals and ERP free text can reach those write tools. The Reflection Agent runs only *after* the side effect has happened.

The implemented config also breaks two binding constraints without a decision. It deploys the model to `eastus`, which the config itself marks as differing from the in-region target (CON-002). It writes every ERP change as `svc-erp-admin`, so no change can be attributed to the technician who made it (CON-003).

At T3, the multi-agent topology (rung 7) has no justification. It duplicates the existing n8n ERP flows (INV-001) and the Azure gateway capability we would expect to exist. It adds roughly 3–5 sequential LLM calls to every turn, against a latency NFR that has never been quantified.

Most of these issues can be fixed with targeted changes; the system does not need to be rebuilt. The direction: one bounded agent, or an LLM-assisted workflow, that calls the existing n8n flows with deterministic, user-scoped authorization and a confirmation step. Several areas have no material issue; they are listed under Recommendations.

### NFR arithmetic (illustrative; figures are `[ASSUMPTION]` / `[UNVERIFIED]`, to be replaced by measurements)

**Latency, by summing per-step p95.** This is an upper approximation of the p95 of the sum, not a measured value. Per-step values: gateway hop ≈ 0.05 s each; Supervisor routing call ≈ 1.5 s; generation call with ~500 output tokens ≈ 5–6 s; Reflection pass ≈ 4 s (≈ 8 s if it rewrites); mobile round trip ≈ 0.5–1 s.

- R1 manuals answer: 1.5 (Supervisor) + 0.5 (embed + Pinecone) + 6 (generate) + 4 (Reflection) + ~0.3 (hops) + 1 (network) ≈ **13 s**.
- R1 history answer: 1.5 + 3 (SQL generation) + 2 (SQL execution) + 5 (answer) + 4 (Reflection) + 1.3 ≈ **17 s**. With one SQL-error self-correction (+5 s) ≈ **22 s**.
- R2 create WO: 1.5 + 3 (tool selection and arguments) + 1 (ERP) + 3 (confirmation text) + 4 (Reflection) + 1.3 ≈ **14 s**. On an ERP timeout with unlimited retry, the turn is capped only by the **120 s** timeout, and the write may still be in flight.
- Runaway loop (no recursion limit): each Supervisor → specialist → Reflection cycle ≈ 10–12 s, so ≈ 10–12 cycles before 120 s. That is ≈ **30–36 LLM calls per message**, against ≈ 3–4 nominally, roughly 10× cost per affected message. Unbounded if the timeout does not cancel the graph.

**Availability, as the product of a serial chain.** Illustrative: AKS 99.95 %, AOAI 99.9 %, custom gateway 99.5 %, Pinecone 99.9 %, ERP API 99.5 %.

- Answer path: 0.9995 × 0.995 × 0.999 × 0.999 ≈ **99.25 %** (excluding the mobile API, identity and network).
- WO path: × 0.995 (ERP) ≈ **98.8 %**.

Both are below the 99.5 % target even before mobile backend, identity and networking are counted. A pure working-hours window helps only if maintenance falls outside it.

**Capacity.** About 400 interactions/day is low. At nominal load, provider quotas are not a material concern. The exposure is runaway loops (F-RT-09), not baseline load.

## Recommendations

- **Rung (R1–R4, AP-03).** *Recommended:* an LLM-assisted workflow, or a single bounded agent. Read tools are RAG over manuals and a parameterized history lookup. The write path is a deterministic confirm-then-submit through the existing n8n flows. Escalation is a deterministic action. *Rejected:* the five-agent plus Supervisor topology, unless an eval demonstrates measured benefit (F-RT-10).
- **ERP writes (R2, R3, CON-003, INV-001).** *Recommended:* reuse n8n, with a least-privilege identity carrying the end user's identity, an idempotency key, bounded retries, deterministic limits and an immutable audit record (F-RT-01–04, F-RT-11).
- **Model access (CON-001, CON-002, DEC-001).** *Recommended:* an in-region AOAI deployment with managed identity, fronted by APIM or an existing gateway if mediation is needed. *Rejected:* the custom gateway with keys in a ConfigMap (F-RT-12). If the required model is not available in-region, escalate the CON-002 conflict; do not choose `eastus`.
- **Vector store (PREF-002).** *Recommended:* an ADR comparing Azure AI Search and Pinecone, with a CON-001 ruling and exit costs (F-RT-13).
- **Logging (CON-002).** *Recommended:* metadata-first telemetry, in-region, short retention, kept separate from the audit store (F-RT-06).

**Areas with no material issue found:**
- **Capacity and quota at nominal volume.** About 400 interactions/day is well within typical AOAI quotas; the risk is runaway loops (covered by F-RT-09), not baseline demand.
- **History DB write protection.** `erp_readonly_replica` against a replica correctly blocks writes. The residual issue is read scope (F-RT-08), not integrity.
- **Functional coverage of R4 (escalation).** A Teams post to dispatch meets the requirement. Only the content-templating hardening in F-RT-07 is needed.
- **LangGraph lock-in.** It is open source and portable at the Python level. Its cost is complexity and skills (F-RT-10), not lock-in.
- **AKS as runtime.** Acceptable within CON-001. Not a finding in itself beyond the availability-model gap (F-RT-15) and whether it is needed at all once the rung is simplified.
- **Overall lock-in.** Low to medium. The only material item is the unrecorded Pinecone exit cost (F-RT-13). There is no big-bang migration plan to attack, because this is new build.

## Positions for the Board

- **The Reflection Agent is not a safety control.** I expect agentic or quality specialists may defend it as a guardrail. Evidence that would change my view: an eval showing it measurably improves answer accuracy, at acceptable latency, and does so *only* on read paths, with writes gated deterministically elsewhere.
- **Bypassing n8n.** The integration side may argue that direct REST is simpler. I would accept the bypass only if n8n cannot carry user identity or an idempotency key, recorded in an ADR, and the direct path reproduces n8n's validation and audit.
- **Severity of F-RT-03 (audit) as Critical.** Someone may argue App Insights is "auditable enough". I hold Critical because the shared admin identity destroys attribution, whatever the log sink. Evidence that would change it: the ERP or n8n records the end user per change today.
- **Severity of F-RT-07 as Critical when injection is "only inferred".** Following the rubric, an exploitable path to write actions is Critical. It is rated Critical on inference because the write tools are verified and the Reflection-after-action ordering is documented. Showing that retrieved and tool content can never reach the WO agent's context would downgrade it.
- **Pinecone and CON-001.** This is a policy interpretation, not a technical one. The CIO/EA should rule. I do not assert a violation.
