# Security, Identity & Governance Architect — fsa-review-fixture — Round 1

## Verdict

**Not viable as proposed.** The implemented configuration lets any text that reaches the model drive ERP create, update and **delete** calls. Those calls run under a shared **ERP admin** service account. There is no human approval, and the only business limits ("max 3 work orders, never EMERGENCY") are written in a system prompt. That combination is a direct path from prompt injection to unauthorized consequential actions. It fails G4: authorization for consequential actions rests on model reasoning.

There are two further problems. Customer and asset data is sent to a model deployment in `eastus`, which the config itself says is not the in-region target. That breaks CON-002 with no decision behind it. And because every ERP change is made by `svc-erp-admin`, with no audit record of the user, agent version or approval, CON-003 cannot be met.

All of this can be fixed inside Azure (CON-001). The fixes are user-delegated identity, deterministic policy at the tool layer, parameter-bound approval, templated reads, an in-region model and logs, and a dedicated audit record. The design is fixable. It is not acceptable in its current form.

**Mandatory controls (T3 minimum, before G4/G5):**
1. Entra ID user authentication, with OBO downscoped per tool or narrow per-tool identities plus a user-entitlement PEP. No admin account (F-SE-01, F-SE-11).
2. Remove the delete tool and put the tool allowlist under change control (F-SE-02).
3. A deterministic PDP/PEP for limits, priority enum, status transitions and idempotency (F-SE-03).
4. System-issued approval bound to a parameter hash (F-SE-04).
5. Privilege separation between agents that read untrusted content and the write tools (F-SE-05).
6. In-region model, logs and stores, enforced by Azure Policy (F-SE-08).
7. A tamper-evident audit record for every work-order change (F-SE-10).
8. Managed identity and Key Vault; no static keys; TLS on every hop (F-SE-07).
9. No raw content in general telemetry (F-SE-09).
10. Templated SQL with row and column scoping (F-SE-06).

## Recommendations

- **Identity for ERP writes (R2, R3, CON-003).** *Recommended:* the user's Entra ID token exchanged OBO and downscoped to the ERP or n8n audience, with effective permission = user ∩ agent. *Alternative:* if the ERP or n8n cannot accept user tokens, a dedicated least-privilege identity per tool, plus a PEP entitlement check and `requested_by` stamping, recorded in an ADR. *Rejected:* the shared `svc-erp-admin` account.
- **Write path.** *Recommended:* call the existing production n8n create/update flows (INV-001) as the only write tools, behind the PEP. This reuses flows the ERP team already governs. The n8n webhooks must authenticate the caller and must not trust payload identity. *Rejected:* direct ERP REST calls from an agent holding admin rights.
- **Business limits (R2, R3).** *Recommended:* PDP in the tool layer, plus schema enums. *Rejected:* system-prompt limits as the control. They may stay as defense in depth only.
- **Approval (R2, R3, Q-001).** *Recommended:* technician confirmation of the structured action, bound to a parameter hash. Out-of-policy requests go to a dispatcher.
- **History reads (R1).** *Recommended:* parameterized query templates. *Alternative:* generated SQL restricted to curated views with RLS, timeout and row cap. *Rejected:* free-form SQL against the full replica.
- **Model residency (CON-002, DEC-001).** *Recommended:* a regional Azure OpenAI deployment in the mandated region, pinned version, Entra auth. *Rejected:* `eastus` or any non-compliant deployment type.
- **Logging (CON-002, CON-003).** *Recommended:* metadata-only telemetry plus a separate audit store. *Rejected:* full prompt and response capture with 730-day retention in App Insights.

## Positions for the Board

- **agentic-systems-architect.** Six agents (Supervisor, Reflection and so on) widen the injection surface and the number of identities and hops to secure. From a security view, a single orchestrator, or a deterministic workflow with typed tools, is easier to authorize and audit. I would not object to multi-agent if it shows measured benefit and each hop propagates user context without amplification. The Reflection Agent is not a security control.
- **integration-infrastructure-architect.** Required boundaries: deny-by-default AKS egress to the approved in-region Azure endpoints; private endpoints for Azure OpenAI, Key Vault, the replica and the audit store; TLS on every internal hop. The implementation is theirs.
- **ai-platform-architect / PREF-003.** A custom in-house gateway is a new security-critical component. I would prefer a managed Azure gateway capability (for example, Azure API Management's AI gateway features) [UNVERIFIED: confirm current feature set], unless the team shows a requirement it cannot meet.
- **data-knowledge-memory-architect / PREF-002.** Pinecone is a third-party SaaS outside Azure. That puts it in tension with CON-001, and with CON-002 if chunks contain asset or customer data. My position is to use an in-region Azure-native store unless the CIO's office confirms Pinecone is within policy. Permission trimming and RLS design for history is theirs; my requirement is that entitlements are enforced at the store, not by the model.
- **reliability-llmops-architect.** Unlimited retries on non-idempotent create and `max_iterations: null` are primarily theirs. My dependency is that idempotency keys and bounded retries are present, so the audit record (F-SE-10) stays one-to-one with changes.
- **red-team-architect.** T-01, T-02 and T-04 are the priority adversarial targets.
- **What would change my mind.** Evidence that the ERP enforces per-technician entitlement on a user-attributed call, or that technicians are legitimately entitled to all maintenance history. Either would lower F-SE-06, and the first would partly close F-SE-01.

- I assume the "in-region" target is an Azure region other than `eastus`, per the config comment.
