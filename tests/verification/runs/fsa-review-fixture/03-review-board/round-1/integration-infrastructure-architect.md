# Integration, Cloud & Infrastructure Architect — fsa-review-fixture — Round 1

## Verdict
**Material gaps.** Azure is the right platform (CON-001) and the workload is small (about 400 interactions/day, no self-hosted models), so a lean managed-PaaS design can carry it. The design as drafted and as implemented has the following problems:
- **Model region:** the configured model region (`eastus`) is flagged in the config itself as different from the in-region target. That conflicts with CON-002.
- **ERP integration:** the Work Order Agent calls the ERP REST API directly with a shared admin account and unlimited retries. This bypasses the production n8n create/update flows (INV-001) and weakens CON-003 auditability.
- **Model gateway:** a custom gateway reached over plain `http://` holds the model key in a ConfigMap. Azure API Management (APIM) already covers this need.
- **AKS:** AKS adds Kubernetes operating cost with no driver for it, such as GPUs, many services, or an existing platform team.
- **Missing infrastructure design:** there is no network design (private endpoints, egress control, DNS), no infrastructure-as-code (IaC) and no environment separation in evidence.

Each item can be fixed with targeted changes inside Azure. A platform redesign is not needed.

## Recommendations
- **ERP integration (R2, R3, CON-003, INV-001).** *Recommended:* reuse the existing n8n create/update flows as the agent's write tools, behind APIM. Each call carries the end-user identity and an idempotency key. Retries are bounded and failures go to a dead-letter queue. *Rejected:* direct ERP REST calls from the agent with `svc-erp-admin`. They duplicate a production investment and degrade auditability.
- **Runtime (NFR-A, NFR-B).** *Recommended:* Azure Container Apps (workload profiles, zone-redundant, VNet-integrated, egress through Azure Firewall). *Alternative:* AKS, only if a platform-team mandate or self-hosted models appear. *Rejected:* AKS as drafted.
- **AI gateway (PREF-003).** *Recommended:* the existing enterprise APIM, or a new private-networking-capable APIM instance, with AI gateway policies and managed identity to Azure OpenAI. *Rejected:* the custom in-house gateway.
- **Model region (DEC-001, CON-002).** *Recommended:* a Regional deployment type in the mandated region, with key auth disabled and public network access off. If the model is unavailable there, raise a constraint conflict to the decision owner.
- **Secrets.** *Recommended:* managed identities everywhere possible, with Key Vault (private endpoint, RBAC) for the rest. No secrets in ConfigMaps or YAML.
- **Network.** *Recommended:* spoke VNet per environment, private endpoints with private DNS for all data and model services, default-deny FQDN egress.
- **IaC and environments.** *Recommended:* Bicep or Terraform with Azure Policy as code, subscription per environment, an ERP sandbox through n8n for non-prod, and CI drift detection.

## Positions for the Board
- **solution-architect / agentic:** collapsing to one bounded agent (or a workflow with LLM steps) shrinks the runtime to one service, which strengthens the Container Apps case. If the board keeps multi-agent, my runtime recommendation still holds at this volume.
- **security-identity-architect:** the `erp_delete_work_order` tool, the ERP-admin role, and authorization by prompt ("never more than 3 work orders") belong to them. My contribution: network-level denial of direct ERP access, and n8n flows exposing only create and update-status. On-behalf-of user identity propagation through APIM to n8n needs their design.
- **data-knowledge-memory-architect:** vector store selection. From the platform side, Pinecone is a third-party SaaS whose Azure private connectivity and in-region availability would need proof against CON-001/CON-002. An Azure-native store with a private endpoint is simpler. Evidence that would change my view: an enterprise-approved Pinecone deployment in the mandated region over Private Link.
- **reliability-llmops-architect:** the "AKS is highly available" DR claim. I provide a zone-redundant single-region topology. Cross-region failover would likely conflict with CON-002 unless a second in-region-compliant region exists.
- **ERP/integration team (stakeholder):** whether the n8n flows can accept an idempotency key and end-user attribution. If they cannot, the remediation is a small change to the flows, not a bypass.
